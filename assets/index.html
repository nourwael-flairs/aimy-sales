Aimy Design System

Build consistent.
Ship confident.

The shared foundation for the whole Aimy ecosystem — one token layer, one component library, and the shared AiMY chat canvas. Everything here is product-agnostic, so any Aimy product can build on it and feel native to the same family.

Ecosystem Light & Dark Urbanist + Poppins
How it's organized

Three layers: tokens → components → the shared AiMY canvas. Products consume the layers below, never the reverse.

🎨
Foundations
Layer 1 · Tokens
Color, typography, spacing, radius, motion, shadow, and layout — one source of truth. Every value is a CSS variable, so light/dark and per-product accents are a single swap.
🧩
Components
Layer 2 · Building blocks
Buttons, forms, cards, badges, chips, dropdowns, overlays, tables, feedback, and data-viz primitives. Product-agnostic — combine them to build any Aimy surface.
✨
AiMY Canvas
Layer 3 · Shared AI surface
The shared chat experience — float input bar, message thread, suggestion chips, and toasts. Drop it into any product that needs an AiMY assistant and it behaves identically everywhere.
Principles
Principle What it means
Token-first No hard-coded colors or spacing in product code — consume the variables so themes and accents propagate automatically.
Product-agnostic Components carry no product-specific copy or logic. Each product themes the accent and supplies its own content.
Theme-aware Every surface works in both light and dark. Test both before shipping a new component.
Accessible by default Focus-visible rings, reduced-motion support, and AA contrast ship with each component — not bolted on later.

Type Cards

Eight templates for eight kinds of knowledge object, sharing one fixed governance row. Type changes what a reader needs to see first — a Ticket without its resolution is useless, an ICP without its disqualifiers is misleading, a Success Story without its approval state is a legal exposure. A single template forces every type into the fields of whichever type it was designed around, and the fields that matter most end up in a drawer.

What never moves. Type · trust state · title · owner · last verified · one classified action sit in the same position on all eight templates. Someone scanning mixed results must not have to relearn where trust lives per type. Only the zone between the title and the governance row varies.

Compact form — .is-compact

Trust State

Whether a piece of content can be relied on — and whether the AI is still allowed to answer from it. A required field on every knowledge object, and the one indicator that must survive leaving its home product: an expired card has to read as expired inside a consuming agent's canvas, inside an embedded panel, anywhere it is cited. A trust indicator that only renders at home is worse than none at all, because it teaches people that no warning means safe.

Trust state is not work state. Work state says what AiMY has done with an item; trust state says whether the item's content holds. An object can be drafted and expired at the same time — AiMY has proposed an update, and the content currently published is past review. Collapsing the two loses the distinction exactly where it carries the most weight.
